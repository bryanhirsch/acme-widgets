# ADR 0003: Self-Registering Widget Presets

- **Status:** Accepted
- **Date:** 2026-05-26
- **Deciders:** Bryan
- **Related:** [ADR 0002 — Dynamic Widget Catalog](./0002.ADR.DYNAMIC_WIDGET_CATALOG.md)

## Context

A "widget" on the site is two things stitched together at render time:

1. **Catalog data** — a row in the Google Sheet (or its CSV fallback at
   `public/data/widgets.csv`): `type`, `description`, `number_in_stock`,
   `price`, `icon`, `categories`.
2. **Visual preset** — a small React component (a "hero" panel: gradient,
   label, cog icon) that gives the card its character. Today, all fifteen
   presets live in `src/components/widgetPresets.tsx` and are looked up
   via a single `widgetPresets: Record<string, Preset>` object keyed by
   the `icon` filename (e.g. `brass-widget.svg` → `Brass`).

The two halves connect through one column. `WidgetCard` does:

```ts
const preset = widgetPresets[widget.icon] ?? standardPreset;
```

`widget.icon` is the value of the `icon` cell in the sheet. If the sheet
says `brass-widget.svg`, the registry's `'brass-widget.svg'` entry is
used. If the sheet says something the registry doesn't know about, the
card falls back to `Standard`. The `.svg` suffix is historical — there
is no real `brass-widget.svg` file on disk (only
`public/icons/placeholder.svg` exists). The string is just a registry
key shaped like a filename.

That contract works fine at 15 widgets. It does not scale to the
workflow the rest of the system is designed for.

ADR 0002 deliberately makes adding catalog **data** a no-code,
no-PR operation: producers append rows to the sheet and the live site
picks them up within minutes. But adding a **new visual style** still
means editing `widgetPresets.tsx` — a single file with one append-only
registry object at the bottom. Two consequences:

1. **The registry is a serialization point.** N agents (or humans) each
   adding a preset all edit the same object literal in the same file.
   Every parallel branch conflicts on the registry block. The work is
   embarrassingly parallel in nature but artificially serial in
   practice.
2. **Visual work and catalog work drift.** A new row can be added to
   the sheet immediately; the matching visual lands days later in a
   PR. The fallback to `Standard` makes this safe but invisible —
   nothing on the site or in the repo tells you that
   `meteor-widget.svg` is referenced by the sheet but has no preset
   defined.

## Decision

### Per-preset files

Move each preset to its own file under `src/components/presets/`,
one file per preset, named after the registry key it owns:

```
src/components/presets/
  brass-widget.tsx
  steel-widget.tsx
  pocket-widget.tsx
  ...
  _standard.tsx       # the fallback; leading underscore keeps it
                      # out of the auto-discovery glob
  _shared.tsx         # CogEl, cogClass, shared types
```

Each preset module has a single default export of type `Preset`. No
registry edit is required to add one — dropping a new file into
`src/components/presets/` is the entire change.

### Auto-discovery via `import.meta.glob`

The registry is built at module-load time by Vite's
[`import.meta.glob`](https://vitejs.dev/guide/features.html#glob-import),
which expands at build into a static map of `path → module`. Roughly:

```ts
// src/components/widgetPresets.ts
import type { Preset } from './presets/_shared';
import standardPreset from './presets/_standard';

const modules = import.meta.glob<{ default: Preset }>(
  './presets/[a-z]*.tsx',
  { eager: true },
);

export const widgetPresets: Record<string, Preset> = Object.fromEntries(
  Object.entries(modules).map(([path, mod]) => {
    const key = path.replace(/^\.\/presets\//, '').replace(/\.tsx$/, '');
    return [`${key}.svg`, mod.default];
  }),
);

export { standardPreset };
```

`WidgetCard` is unchanged: `widgetPresets[widget.icon] ?? standardPreset`
still works because the generated registry has the same shape.

### How sheet data matches a preset

The contract between the catalog and the visual layer is **one column:
`icon`**. The mapping is:

| Sheet cell (`icon`)   | Preset file path                          |
| --------------------- | ----------------------------------------- |
| `brass-widget.svg`    | `src/components/presets/brass-widget.tsx` |
| `steel-widget.svg`    | `src/components/presets/steel-widget.tsx` |
| `meteor-widget.svg`   | *(no file)* → falls back to `_standard`   |
| *(empty)*             | row is skipped by `parseWidgetsCsv`       |

The rule:

1. Strip the `.svg` suffix from the `icon` cell.
2. Look for `src/components/presets/<that-name>.tsx`.
3. If present, its default export is the preset.
4. If absent, render `_standard.tsx`.

Producers editing the sheet do not need to know this mapping exists —
they pick from a documented list of available `icon` values, the same
way they do today. Engineers adding a new visual style add a file at
the path that matches the `icon` value the sheet will use.

### Documenting available icons

Today the list of valid `icon` values is implicit — you discover them
by reading `widgetPresets.tsx`. With per-file presets, the list of
valid values is the contents of `src/components/presets/` (minus the
leading-underscore files). Generate a short reference table in
`docs/current/EDITING_THE_CATALOG.md` from that directory at build time,
or maintain it by hand — either way, the source of truth is the
filesystem, not a registry object.

### Naming and validation

- **Filenames are lowercase, hyphenated**, matching the `icon` column
  convention (`brass-widget.tsx`, not `BrassWidget.tsx`).
- **Files starting with `_`** (`_standard.tsx`, `_shared.tsx`) are
  excluded from the glob. The leading-underscore convention is what
  makes the discovery rule unambiguous.
- **A unit test** asserts that every preset file's default export
  satisfies the `Preset` type and that the generated registry has no
  duplicate keys. This catches a malformed preset at CI time rather
  than at render time.
- **No runtime check** that every `icon` value in the sheet has a
  matching file. That would re-introduce the kind of build-time
  coupling between catalog data and code that ADR 0002 explicitly
  rejected. The `_standard` fallback remains the contract for
  unknown icons.

## Consequences

**Positive**

- Adding a new visual preset is a single new file. N engineers or
  agents can add N presets on N branches with zero merge conflicts on
  shared registry code.
- The pairing between an `icon` cell value and a preset is now visible
  on the filesystem — `ls src/components/presets/` is the list of
  supported icons.
- `widgetPresets.tsx` shrinks from ~350 lines of mixed registry-and-
  styling to a ~15-line generator. Visual code lives next to the
  preset it belongs to.
- The `WidgetCard` consumer is unchanged; the public API of
  `widgetPresets` and `standardPreset` is preserved, so this is a
  pure refactor at the call site.

**Negative / accepted trade-offs**

- `import.meta.glob` is a Vite-specific feature. We are already
  committed to Vite by ADR 0001, so this does not add a new lock-in,
  but it does deepen the existing one. A move off Vite would need to
  replace the glob with an explicit `index.ts` re-export.
- The mapping rule (strip `.svg`, look up filename) is one indirection
  more than the current explicit object literal. The trade-off is
  fewer touch points per change in exchange for one documented rule.
- Eager glob loading bundles every preset into the initial chunk, the
  same as today. If the preset count grows large enough that this
  matters (it does not at 15 or even 100), switching to a lazy glob
  and `React.lazy` is a follow-up — out of scope here.

## Alternatives considered

- **Status quo.** Rejected: the registry-as-bottleneck problem is the
  whole reason this ADR exists.
- **One file per preset, manual `index.ts` re-export.** Splits the
  per-file work cleanly but reintroduces a single shared file
  (`index.ts`) that every new preset has to edit. Solves half the
  problem.
- **Runtime registration via side-effectful `register()` calls inside
  each preset module.** Works, but depends on every module being
  imported for its side effect, which is fragile under tree-shaking
  and requires a barrel file anyway. The `import.meta.glob` approach
  gets the same effect declaratively and statically.
- **Move presets into the catalog data itself** (e.g. a `preset_json`
  column in the sheet describing the hero panel). Rejected: presets
  are React components with Tailwind classes and Heroicons imports,
  not data. Embedding them in the sheet would either restrict them to
  a tiny declarative subset or invite arbitrary JSX-in-a-cell, both
  worse than the current split.

## Open questions

- **Naming the fallback.** `_standard.tsx` keeps the fallback out of
  the glob and signals "not user-pickable." If we ever want
  `standard-widget.svg` in the sheet to render the same visual,
  re-export `_standard` from a regular `standard-widget.tsx`.
- **Generated icon reference in `EDITING_THE_CATALOG.md`.** Worth a
  short script in `package.json` (`bun run docs:icons`) or kept
  manual? Defer until the preset count grows past ~30.
